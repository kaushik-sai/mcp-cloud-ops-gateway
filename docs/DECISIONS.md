# Decisions

Numbered and append-only. A changed decision gets a new row that names the one it replaces.

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Language | Go 1.25 | Cloud and Kubernetes tooling is mostly Go (kubectl, Terraform, most operators). One static binary, small distroless image, fast start, strong standard library for HTTP, crypto and exec. |
| 2 | MCP implementation | Official MCP Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0) | Maintained with the spec authors, supports stdio and streamable HTTP, typed tools with schema inference and validation, and bearer-token middleware. Writing JSON-RPC by hand would be more code to secure. |
| 3 | Policy engine | Own evaluator over YAML, not OPA/Rego or Cedar | The rules needed (tool glob, argument conditions, most-restrictive-wins) fit in ~300 lines that are pure and easy to test. OPA adds a large dependency and a language reviewers must learn. The `Policy.Evaluate` signature is small enough to back with OPA later if rules outgrow YAML. |
| 4 | Conflict resolution between rules | Most restrictive effect wins (deny > ask > allow); default deny | No priorities or ordering to reason about. Exceptions are written as narrower ask/deny rules next to a broad allow. Adding a rule can only make a profile stricter, unless it is an allow for something nothing else matches. |
| 5 | Where approvals happen | A separate admin listener and token list; not MCP elicitation | Elicitation goes back to the MCP client, which may be the agent itself. A human approval must come through a channel the agent cannot drive. |
| 6 | What an approval covers | SHA-256 digest of principal, tool and arguments (defaults filled, justification and approval_id excluded); single use; 15 min to decide, 5 min to use | Stops reuse for a different call and replay of the same call. Justification is shown to the approver but does not change the call. |
| 7 | Arguments the policy sees | Every input field, including zero values and defaults, via reflection (ignoring `omitempty`) | Found by a test: with `omitempty`, an agent that left `dry_run` out skipped the "ask when dry_run is false" rule. The policy must see what will actually run. |
| 8 | How tools reach platforms | CLIs (`kubectl`, `aws`, `terraform`) through one runner; Azure through ARM REST | CLIs are what operators already trust and debug with, and the runner is one mockable seam. Azure CLI only accepts a federated token on the command line (visible in the process list), so Azure uses the REST API with a bearer header instead. |
| 9 | Shell use | None. argv only, minimal environment | Removes command injection as a class and keeps the gateway's own environment out of tools. |
| 10 | Credentials | OIDC token exchange (AWS STS web identity, Entra workload identity federation) per tool group, separate read and write identities | No static keys to leak or rotate. Credentials last minutes. A bug in a read tool cannot use write permissions. |
| 11 | Cloud SDKs | Not used; token exchanges are two documented HTTP calls | Keeps the dependency tree to two modules and the code readable. |
| 12 | Kubernetes Secrets | Not readable through the gateway at all, whatever the policy says | The value an agent gets from a Secret is never worth the risk of it landing in a prompt or a log. |
| 13 | Audit format | JSON lines with a SHA-256 hash chain, fsync per record, optional stderr mirror | Readable with `jq`, shippable by any log agent, tamper-evident without a database. Write-once storage downstream makes it tamper-proof. |
| 14 | Audit failure | Fail closed: no decision record, no call | An unaudited change is worse than a failed one. |
| 15 | Target naming | Aliases chosen by the operator (Terraform workspaces, Azure subscriptions) | Agents never pass paths or IDs, so they cannot point a tool at something the operator did not list. |
| 16 | Prompt-injection handling | Fence output, flag likely injections, redact secrets; rely on policy and approvals for safety | Detection is heuristic and will miss things; the structural controls do not depend on it. |
| 17 | Config replication | One YAML per environment with `${ENV}` expansion (unset variable is an error); Kustomize base plus overlays | The same file moves between environments unchanged; only variables and overlays differ. A missing variable fails start-up instead of becoming an empty string. |
| 18 | Approval storage and scaling | In memory, single replica for deployments that serve `ask` rules | Simple and correct for v0.1. Next step: a `Store` behind the broker's five methods (Create, Decide, Consume, Get, List) backed by Redis or Postgres, so ops deployments can run several replicas. Read-only deployments can already scale out. |
| 19 | Local Kubernetes for tests | kwok (real kube-apiserver and etcd, simulated nodes) in this build environment; kind in docs | kind's control plane would not start on this host's cgroup v1. kwok runs the real API server, so RBAC, validation, scale and patch behave as on a real cluster. Pod logs need a kubelet and are not covered by the e2e run. |
| 20 | CI shape | Same governance as governed-repo-template: required checks lint, test, build, workflow-lint, secret-scan, vulncheck, dependency-review, pr-policy; actions pinned by SHA; tools verified by SHA-256; read-only token | One standard across the portfolio. Go jobs use bash; PR policy reuses the template's PowerShell script unchanged. |
| 21 | Go toolchain pin | `go 1.25.0` minimum with `toolchain go1.25.14` | Library users can build with any 1.25.x; CI and releases use the latest patch so govulncheck does not flag fixed standard-library CVEs. |
| 22 | Container image | Distroless static, nonroot, kubectl pinned by SHA-256, base images pinned by digest | No shell or package manager in the runtime image; reproducible builds. aws CLI and terraform are not in the default image (size); build a variant when those groups are enabled. |
